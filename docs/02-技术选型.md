# 02 - 技术选型

这里列出每个环节的候选 crate / 技术，并说明取舍。优先选成熟、跨平台、社区活跃的方案。

## 1. Web 服务器 + WebSocket

**选型：[`axum`](https://github.com/tokio-rs/axum) + [`tokio`](https://tokio.rs/)**

- `axum` 基于 tokio，原生支持 WebSocket 升级（`axum::extract::ws`），同时能托管静态文件。
- 一个框架同时搞定「托管前端」+「WebSocket 通信」+「TLS」，依赖统一。
- TLS 用 [`axum-server`](https://github.com/programatik29/axum-server) + [`rustls`](https://github.com/rustls/rustls)，纯 Rust，无需系统 OpenSSL。

备选：`actix-web`（功能强但更重）、`warp`（维护趋缓）。`axum` 是当前 tokio 生态主流。

## 2. 屏幕捕获

跨平台捕获没有一个完美的统一 crate，建议**抽象 trait + 分平台选库**：

| 平台 | 方案 | 说明 |
| --- | --- | --- |
| 通用首选 | [`scap`](https://github.com/CapSoftware/scap) 或 [`xcap`](https://github.com/nashaofu/xcap) | 跨平台截屏库，API 简单；`scap` 偏向流式捕获，`xcap` 偏向单张截图 |
| Linux X11 | [`x11rb`](https://github.com/psychon/x11rb) 直接调用 `XGetImage` / SHM 扩展 | 需要高帧率时直接用 SHM (`MIT-SHM`) 避免每帧拷贝开销 |
| Windows | [`windows`](https://github.com/microsoft/windows-rs) crate 调 Desktop Duplication API (DXGI) | 微软官方维护，DXGI 是 Windows 下高效捕获的标准方案 |
| Wayland | （预留）PipeWire + `xdg-desktop-portal` | 接口预留，暂不实现 |

**建议路线**：先用 `scap` 跑通流式捕获验证端到端链路；若 X11/Windows 帧率或延迟不达标，再针对性下沉到 `x11rb`(SHM) 和 DXGI 自实现。trait 抽象保证下沉时上层不动。

## 3. 视频编码

这是性能和体验的关键。需要在「编码质量/CPU 占用/延迟/集成难度」之间权衡。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **OpenH264** ([`openh264`](https://github.com/ralfbiedert/openh264-rs) crate) | 纯软件 H.264，跨平台一致，Cisco 维护，集成简单，浏览器解码支持好 | CPU 编码，高分辨率高帧率下占用较高 |
| FFmpeg 绑定 ([`ffmpeg-next`](https://github.com/zmwangx/rust-ffmpeg)) | 功能最全，可调用硬件编码(NVENC/QSV/VAAPI) | 依赖系统 FFmpeg 库，编译/分发复杂 |
| VPX/VP8-VP9 ([`vpx` 绑定]) | 浏览器原生支持好 | Rust 绑定生态不如 H.264 成熟 |
| 硬件编码(平台原生) | 延迟低、CPU 占用低 | 各平台 API 不同，复杂度高 |

### 推荐

**第一阶段用 `openh264`**：纯软件、跨平台行为一致、浏览器解码无障碍，最快跑通。
**第二阶段**（若性能不足）：抽象出 `Encoder` trait，增加 FFmpeg 硬件编码后端（VAAPI on Linux / NVENC / QSV），软件编码作为 fallback。

编码参数建议：

- baseline/constrained baseline profile，保证浏览器 WebCodecs/MSE 兼容性最好
- 低延迟模式：关闭 B 帧，小 GOP，`tune zerolatency` 思路
- 码率自适应：根据分辨率设默认码率，预留运行时调整接口

> 颜色空间：捕获通常得到 BGRA/RGBA，编码器需要 YUV420（I420）。这步转换 CPU 开销不小，建议用 SIMD 优化的库（如 `dcv-color-primitives` 或 `libyuv` 绑定），或直接用编码器/FFmpeg 自带的转换。

## 4. 浏览器端视频解码

| 方案 | 说明 | 兼容性 |
| --- | --- | --- |
| **WebCodecs API** (`VideoDecoder`) | 直接解码 H.264 NAL 单元，延迟最低，最适合实时流 | Chrome/Edge 完整支持，Firefox 较新版本支持，Safari 部分支持 |
| **MSE** (Media Source Extensions) | 把 H.264 封装成 fMP4 喂给 `<video>` | 兼容性更广，但需封装 fMP4，延迟略高 |
| WebRTC | 浏览器原生低延迟视频 | 需要 SDP/ICE 协商，对局域网直连场景偏重 |

### 推荐

**首选 WebCodecs**：延迟最低，直接吃 H.264 码流，配合 `<canvas>` 渲染，最契合实时控制场景。
**MSE 作为 fallback**：对不支持 WebCodecs 的浏览器，被控端额外提供 fMP4 封装。

> 没选 WebRTC 的原因：局域网直连场景下，WebRTC 的 ICE/STUN/TURN 协商是额外复杂度，收益不明显。WebSocket + WebCodecs 在直连下延迟已足够低，且协议简单可控。架构上预留了切换空间，未来需要公网穿透时可引入 WebRTC。

## 5. 输入注入

| 平台 | 方案 |
| --- | --- |
| 通用首选 | [`enigo`](https://github.com/enigo-rs/enigo) —— 跨平台模拟鼠标键盘，API 统一，支持 Linux/Windows/macOS |
| Linux X11 | `enigo` 底层用 XTEST；或直接 `x11rb` 调 `XTEST` 扩展 |
| Windows | `enigo` 底层用 `SendInput`；或直接 `windows` crate |
| Wayland | （预留）`enigo` 对 Wayland 输入支持有限，需评估 `ydotool`/uinput 方案 |

**建议**：先用 `enigo` 跑通，它已覆盖 X11 和 Windows。若遇到特殊按键映射、组合键、相对移动等需求 `enigo` 满足不了，再下沉到平台 API。

> 键码映射是个坑：浏览器发的是 [`KeyboardEvent.code`](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code)（如 `KeyA`、`Enter`、`ShiftLeft`），需要映射到 `enigo` 的 `Key` 枚举或平台原生键码。需要一张映射表，这是协议层要明确定义的（见 [03-通信协议.md](03-通信协议.md)）。

## 6. 序列化 / 协议编解码

| 用途 | 选型 |
| --- | --- |
| 控制/输入消息 | JSON（[`serde_json`](https://github.com/serde-rs/json)）—— 调试友好，输入事件量不大，性能足够 |
| 视频帧 | 自定义二进制帧头 + 原始 H.264 数据 —— JSON 不适合二进制大数据 |

WebSocket 同时支持文本帧和二进制帧：**文本帧走 JSON 控制消息，二进制帧走视频数据**，天然区分。

## 7. 其他基础 crate

| 用途 | crate |
| --- | --- |
| 异步运行时 | `tokio` |
| 错误处理 | `anyhow`（应用层）+ `thiserror`（库层定义错误类型） |
| 日志 | `tracing` + `tracing-subscriber` |
| 配置/参数 | `clap`（命令行）+ `serde` + `toml`（配置文件） |
| 密码哈希 | `argon2` 或 `sha2`（简单密码场景，见安全文档） |
| TLS | `rustls` + `rcgen`（自动生成自签名证书） |

## 选型总结（第一阶段最小集）

```
axum + tokio          Web/WS 服务器
rustls + rcgen        TLS + 自签证书
scap                  屏幕捕获（跨平台起步）
openh264              视频编码（软件 H.264）
enigo                 输入注入（跨平台）
serde + serde_json    协议编解码
WebCodecs (浏览器)     视频解码
tracing / clap / anyhow  基础设施
```

先用这套最小集打通端到端，再按瓶颈逐步替换高性能后端（DXGI/SHM 捕获、硬件编码）。
