# 03 - 通信协议

浏览器与被控端通过单条 WebSocket（wss）连接通信。利用 WebSocket 同时支持文本帧和二进制帧的特性：

- **文本帧** → JSON 控制消息（握手、认证、输入事件、状态）
- **二进制帧** → 视频数据（带自定义帧头）

## 1. 连接与握手流程

```
浏览器                                      被控端服务
  │                                            │
  │ ── HTTP GET /ws (Upgrade: websocket) ────> │
  │ <───────── 101 Switching Protocols ─────── │
  │                                            │
  │ <──────── {type:"hello", ...} ──────────── │  服务端发送能力声明
  │                                            │
  │ ── {type:"auth", token:"..."} ──────────>  │  浏览器提交认证
  │                                            │
  │ <──── {type:"auth_ok"/"auth_fail"} ──────  │  认证结果
  │                                            │
  │ <──── {type:"screen_info", ...} ────────── │  屏幕分辨率信息
  │ <════════ 二进制视频帧 (IDR起画) ══════════ │  开始推流
  │                                            │
  │ ── {type:"input", ...} ─────────────────>  │  浏览器持续发送输入
  │ ── {type:"input", ...} ─────────────────>  │
  │ <════════ 二进制视频帧 ════════════════════ │  服务端持续推流
```

认证未通过前，服务端不推送任何视频帧，也不处理任何输入事件。

## 2. 文本控制消息（JSON）

所有控制消息形如 `{ "type": "<消息类型>", ... }`。

### 2.1 服务端 → 浏览器

**hello** —— 连接建立后服务端首先发送，声明能力：

```json
{
  "type": "hello",
  "version": "1.0",
  "auth_required": true,
  "video_codec": "h264",
  "delivery": "webcodecs"
}
```

**auth_ok / auth_fail**：

```json
{ "type": "auth_ok", "session_id": "uuid" }
{ "type": "auth_fail", "reason": "invalid_password" }
```

**screen_info** —— 屏幕信息，浏览器用于坐标换算和初始化解码器：

```json
{
  "type": "screen_info",
  "width": 1920,
  "height": 1080,
  "displays": [ { "id": 0, "x": 0, "y": 0, "width": 1920, "height": 1080 } ]
}
```

**error** —— 通用错误：

```json
{ "type": "error", "code": "encoder_failed", "message": "..." }
```

### 2.2 浏览器 → 服务端

**auth** —— 提交认证：

```json
{ "type": "auth", "token": "<密码或登录后下发的token>" }
```

**input** —— 输入事件（核心，见下一节）。

**control** —— 客户端控制请求：

```json
{ "type": "control", "action": "request_keyframe" }   // 请求关键帧（丢包后恢复）
{ "type": "control", "action": "set_quality", "bitrate": 4000000 }  // 调码率
{ "type": "control", "action": "select_display", "id": 1 }  // 多屏切换
```

**ping/pong** —— 心跳（也可用 WebSocket 内置 ping/pong）。

## 3. 输入事件协议

输入事件是 `type:"input"` 消息，用 `event` 字段区分具体类型。

### 3.1 坐标约定

**统一用归一化坐标**：`x`、`y` 为 0.0~1.0 的浮点数，相对于视频画面宽高。被控端按当前屏幕分辨率换算成像素：

```
px = round(x * screen_width)
py = round(y * screen_height)
```

这样前端无论怎么缩放显示窗口，坐标都不会错位。

### 3.2 鼠标事件

```json
{ "type": "input", "event": "mouse_move", "x": 0.523, "y": 0.418 }

{ "type": "input", "event": "mouse_down", "button": "left", "x": 0.523, "y": 0.418 }
{ "type": "input", "event": "mouse_up",   "button": "left", "x": 0.523, "y": 0.418 }

{ "type": "input", "event": "wheel", "dx": 0, "dy": -120 }
```

- `button` 取值：`left` / `right` / `middle`
- `mouse_move` 高频，前端应做节流（如合并到 ~60~120Hz）或只在移动时发送

### 3.3 键盘事件

```json
{ "type": "input", "event": "key_down", "code": "KeyA", "modifiers": ["shift"] }
{ "type": "input", "event": "key_up",   "code": "KeyA", "modifiers": ["shift"] }
```

- `code` 直接采用浏览器 [`KeyboardEvent.code`](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code) 的物理键值（如 `KeyA`、`Digit1`、`Enter`、`ArrowUp`、`ShiftLeft`、`ControlLeft`）。
- 选用 `code` 而非 `key`，是因为 `code` 表示物理按键位置，与键盘布局无关，映射到平台键码更可靠。
- `modifiers`：当前按下的修饰键列表，取值 `shift` / `ctrl` / `alt` / `meta`，便于被控端校正组合键状态。

### 3.4 键码映射

被控端维护一张 `KeyboardEvent.code` → 平台键码（或 `enigo::Key`）的映射表。这是必须明确实现的部分：

```
"KeyA"        → Key::Unicode('a') / XK_a / VK_A
"Enter"       → Key::Return
"ShiftLeft"   → Key::Shift
"ArrowUp"     → Key::UpArrow
"Backspace"   → Key::Backspace
...
```

映射表覆盖：字母数字、功能键(F1-F12)、方向键、修饰键、常用符号、小键盘。少数无法映射的键记录日志并忽略。

## 4. 视频流二进制协议

视频走 WebSocket 二进制帧。每个二进制帧 = **固定帧头 + H.264 负载**。

### 帧头格式（小端，共 16 字节）

```
偏移  长度  字段          说明
0     1     magic         固定 0xRC (标识)
1     1     frame_type    1=关键帧(IDR)  2=非关键帧(P帧)  3=参数集(SPS/PPS)
2     2     reserved      预留对齐
4     4     sequence      帧序号，递增，用于检测丢帧/乱序
8     8     timestamp_us  捕获时间戳（微秒），用于解码端节奏控制
16    ...   payload       H.264 Annex-B 码流（含起始码）
```

设计要点：

- **frame_type** 让解码端识别关键帧，新连接接入或丢包恢复时定位 IDR。
- **sequence** 让浏览器检测丢帧；连续丢帧时可发 `request_keyframe`。
- **timestamp** 用于浏览器端平滑渲染节奏（避免忽快忽慢）。
- 采用 **Annex-B 格式**（带 `00 00 00 01` 起始码），WebCodecs 配置为 annexb 模式可直接喂入。
- 大帧可能超过单个 WebSocket 帧，但 WebSocket 协议本身会处理分片，应用层一般无需手动切分；若编码帧过大，可在帧头加分片字段（预留 reserved 空间）。

### 解码端处理

```
收到二进制帧 → 解析帧头 → 检查 sequence 连续性
  → frame_type==3(参数集): configure VideoDecoder
  → frame_type==1(IDR):    decode (key)
  → frame_type==2(P):      decode (delta)
  → 解码出的 VideoFrame → 绘制到 canvas
```

## 5. 消息类型一览

| 方向 | type/event | 帧类型 | 用途 |
| --- | --- | --- | --- |
| S→C | hello | 文本 | 能力声明 |
| C→S | auth | 文本 | 提交认证 |
| S→C | auth_ok / auth_fail | 文本 | 认证结果 |
| S→C | screen_info | 文本 | 屏幕信息 |
| C→S | input(mouse_move/down/up/wheel) | 文本 | 鼠标 |
| C→S | input(key_down/key_up) | 文本 | 键盘 |
| C→S | control | 文本 | 关键帧请求/调码率/切屏 |
| S→C | error | 文本 | 错误 |
| 双向 | ping/pong | 文本 | 心跳 |
| S→C | (视频帧) | 二进制 | H.264 码流 |

## 6. 版本协商

`hello` 消息带 `version` 字段。后续协议升级时，浏览器和服务端可据此协商，保证向后兼容。第一版固定 `"1.0"`。
