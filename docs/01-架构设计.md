# 01 - 架构设计

## 1. 总体架构

整个系统由两个部分组成：

- **被控端服务（Rust）**：运行在被控制的电脑上，是系统的核心。单一可执行文件，内嵌 Web 服务器。
- **Web 前端（浏览器）**：用户操作界面，纯静态资源（HTML/JS/CSS），由被控端服务托管。

无需独立的后端服务器，无需数据库。被控端服务本身就是后端。

```
                         被控端电脑 (Linux X11 / Windows)
┌──────────────┐        ┌────────────────────────────────────────────┐
│   浏览器      │        │              Rust 被控端服务                  │
│              │        │                                              │
│ ┌──────────┐ │  wss   │ ┌──────────┐  ┌──────────┐  ┌─────────────┐ │
│ │ 视频解码  │<├────────┼─│ Web服务器 │──│ 会话管理  │  │  屏幕捕获     │ │
│ │ (WebCodec│ │ 视频流  │ │(axum +   │  │(认证/状态)│<─│  (平台抽象)   │ │
│ │  /MSE)   │ │        │ │ ws)      │  └──────────┘  └──────┬──────┘ │
│ └──────────┘ │        │ └────┬─────┘                       │        │
```

## 2. 被控端模块划分

按职责拆成几个 Rust 模块（后续可演化为多个 crate）：

```
remotecontrol-server/
├── main           程序入口、参数解析、配置加载
├── web            HTTP 服务器、静态资源托管、WebSocket 升级
├── session        会话管理、认证状态机、生命周期
├── protocol       消息编解码（输入事件、视频帧、控制消息）
├── capture        屏幕捕获 —— 平台抽象 trait + 各平台实现
├── encoder        视频编码（捕获帧 → H.264 码流）
├── input          输入注入 —— 平台抽象 trait + 各平台实现
└── platform       平台相关的公共工具（屏幕信息、坐标换算等）
```

### 2.1 平台抽象

跨平台是核心难点。用 trait 把平台差异隔离在 `capture` 和 `input` 两个模块里：

```rust
// capture 模块
pub trait ScreenCapturer: Send {
    /// 返回屏幕分辨率等信息
    fn info(&self) -> ScreenInfo;
    /// 抓取一帧，返回原始像素（BGRA/RGBA）
    fn grab_frame(&mut self) -> Result<Frame>;
}

// input 模块
pub trait InputInjector: Send {
    fn move_mouse(&mut self, x: i32, y: i32) -> Result<()>;
    fn mouse_button(&mut self, btn: MouseButton, pressed: bool) -> Result<()>;
    fn scroll(&mut self, dx: i32, dy: i32) -> Result<()>;
    fn key(&mut self, code: KeyCode, pressed: bool) -> Result<()>;
}
```

各平台分别实现，用条件编译选择：

```rust
#[cfg(all(target_os = "linux", feature = "x11"))]
mod x11;
#[cfg(target_os = "windows")]
mod windows;
#[cfg(all(target_os = "linux", feature = "wayland"))]
mod wayland; // 预留，暂不实现，编译期 feature 关闭
```

工厂函数在运行时返回对应平台的实现：

```rust
pub fn create_capturer() -> Result<Box<dyn ScreenCapturer>> { ... }
pub fn create_injector() -> Result<Box<dyn InputInjector>> { ... }
```

Wayland 的实现先放一个 `unimplemented!()` 占位 + 清晰的报错信息（提示用户在 X11 下运行或等待后续版本），保证接口存在、不破坏编译。

## 3. 线程 / 异步模型

混合模型：异步处理网络 I/O，独立线程处理 CPU 密集的捕获和编码。

```
┌─────────────────────────────────────────────────────────────┐
│ Tokio 运行时（异步）                                            │
│                                                               │
│  ┌──────────────┐   每个 WebSocket 连接一个 task              │
│  │ ws 接收 task  │ ──> 解析输入事件 ──> mpsc ──> 输入注入       │
│  └──────────────┘                                             │
│  ┌──────────────┐                                             │
│  │ ws 发送 task  │ <── broadcast/mpsc <── 视频帧              │
│  └──────────────┘                                             │
└───────────────────────────────────────────▲──────────────────┘
                                             │ 编码后的帧
┌────────────────────────────────────────────┴─────────────────┐
│ 捕获+编码线程（专用 std::thread，非异步）                       │
│   循环: grab_frame() → encoder.encode() → 发送到 channel      │
│   按目标帧率节流（如 30fps），可根据连接数暂停                  │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│ 输入注入线程（专用 std::thread）                                 │
│   X11/Windows 输入 API 多为非线程安全/需固定线程，单独跑        │
│   从 mpsc 接收事件，串行注入                                    │
└───────────────────────────────────────────────────────────────┘
```

关键设计点：

- **捕获/编码不放进 async**：抓屏和编码是阻塞且 CPU 密集的，放在专用线程，避免拖垮 tokio 调度器。
- **输入注入单线程**：X11 的 `XTEST`、Windows 的 `SendInput` 通常要求在固定线程调用，用专用线程串行处理来自所有连接的事件。
- **channel 连接两端**：线程与 async task 之间用 `tokio::sync::mpsc` / `broadcast` 通信。视频帧用 broadcast（多个浏览器可同时观看），输入事件用 mpsc 汇聚到注入线程。

## 4. 数据流

### 4.1 视频下行（被控端 → 浏览器）

```
屏幕捕获(BGRA帧) → 颜色转换(BGRA→YUV) → H.264编码 → 分片打包 → ws二进制帧 → 浏览器解码 → canvas渲染
```

- 帧率节流：默认 30fps，无观看者时降频或暂停以省 CPU。
- 关键帧策略：新连接接入时强制发一个 IDR 关键帧，保证能立即起画。
- 背压：发送 channel 满时丢弃旧的非关键帧（视频可丢帧，输入不可丢）。

### 4.2 输入上行（浏览器 → 被控端）

```
浏览器事件(mousemove/mousedown/keydown...) → 归一化坐标 → ws文本/二进制 → 解析 → mpsc → 注入线程 → 平台API
```

- 坐标归一化：浏览器以 0~1 的相对坐标或基于视频原始分辨率的坐标发送，被控端换算成屏幕实际像素，避免前端缩放导致错位。
- 顺序保证：mpsc 天然保序，注入线程串行执行，保证按键/点击顺序正确。

## 5. 多连接行为

同一局域网可能有多人连接。设计为：

- 视频流向所有已认证连接广播（共用一个编码器，省资源）。
- 输入默认允许所有已认证连接发送（个人使用场景）。配置项预留「独占控制」开关，后续可加。

## 6. 配置

启动时读取配置（命令行参数 + 可选配置文件），关键项：

- 监听地址/端口
- 访问密码
- TLS 证书路径（不配则自动生成自签名证书）
- 目标帧率、编码码率
- 是否强制独占控制
